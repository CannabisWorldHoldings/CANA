# DATABASE DECISION — orderweeddc on Namecheap Stellar Business (cPanel)

Decision agent: HOST CAPABILITY AND DATABASE DECISION lane (research/analysis only — no repo edits, no provisioning).
Date: 2026-07-26. App: Next.js 16 (`16.3.0-canary.6`) + Prisma 6.19.3, currently SQLite, classified `LOCAL_TEST_DATABASE_ONLY` on measured evidence.

## DECISION

**Use MariaDB 11.4.9 (the host's current-LTS offering), via Prisma's `mysql` provider, on `localhost` of the same cPanel account.**

**PostgreSQL 10.23 is REJECTED — not because PostgreSQL is a bad engine, but because this specific build reached upstream end-of-life on 2022-11-10 and has received no security or bug fixes for ~3 years 8 months.** A hash-chained money ledger must not live on an unpatchable database. "It was available on the host" is not a defence.

**SQLite remains LOCAL_TEST_DATABASE_ONLY** (measured: 10 concurrent handoffs → 10 HTTP 500s before repair; single-writer lock architecture — FIRST-PARTY, `deliverables/MISSION_STATE.json` walls `VERIFICATION_11_H26_REPAIR`, `WRITE_INDEPENDENT_HANDOFF`, `DATABASE_CONFIG_REPRODUCIBLE`; upheld by independent verification in `deliverables/INDEPENDENT_VERIFICATION_12_DATA_PLANE.md`).

**No schema weakening is licensed by this decision.** Both `@@unique([merchantId, seq])` and `@@unique([merchantId, eventIdentity])` are fully enforceable on MariaDB/InnoDB exactly as written. Any port that drops or dilutes a uniqueness constraint to "make the database work" is a defect, not a migration.

## CANDIDATE EVALUATION — every axis, both candidates

| Axis | MariaDB 11.4.9 | PostgreSQL 10.23 |
|---|---|---|
| **Prisma compatibility** | `mysql` provider; Prisma docs explicitly list **MariaDB 10.0+ and 11.0+** as supported self-hosted databases [VD: prisma.io/docs/orm/reference/supported-databases]. App pins Prisma **6.19.3** — the known open bug "SQL syntax error in MariaDB 10.11+ (JSON protocol)" affects **Prisma v7+ only; v6 is explicitly unaffected** [VD: github.com/prisma/prisma#29023]. Schema uses no `Json` type, so the buggy path is doubly avoided. | Prisma docs list PostgreSQL 9.6–18 as supported, including 10 [VD: same page]. Connector compatibility is NOT the disqualifier. |
| **Supported schema features** | Everything this schema uses maps cleanly: composite `@@unique`, `@@index`, FK `onDelete: Cascade/SetNull` (InnoDB), `DateTime` → `DATETIME(3)`, `Float` → `DOUBLE`, `@default(uuid())` is client-side (engine-agnostic) [VD: Prisma MySQL connector docs; FP: schema read]. **Caveat:** Prisma maps `String` → `VARCHAR(191)` on MySQL-family by default [VD: prisma.io MySQL connector docs]; unbounded text columns need `@db.Text` annotations (list below) or long writes fail loudly under strict mode. | Same features supported; `String` → `TEXT` by default, so no annotation work. A genuine ergonomic point for PG — irrelevant against EOL. |
| **Transactional uniqueness (the load-bearing guarantee)** | InnoDB enforces unique indexes atomically at write time under row-level locking; a losing concurrent insert gets a duplicate-key error, surfaced by Prisma as **P2002**, which `demand-credits.mjs::append()` already translates into `DUPLICATE_ATTRIBUTION` / `CHAIN_POSITION_CONTENDED` [FP: code; VD: MariaDB/InnoDB docs]. The check-then-act race the repo measured (50 identical POSTs → 2 committed rows before the constraint existed) is adjudicated by the database on MariaDB exactly as designed. | PG 10 enforces the same guarantee correctly. Equal on correctness. |
| **NULL handling in unique indexes** | **MariaDB UNIQUE indexes permit multiple NULLs** (NULL ≠ NULL) [VD: mariadb.com/docs/server/reference/data-types/null-values, mariadb-indexes-guide]. This is **identical to SQLite and to PostgreSQL's default (NULLS DISTINCT)** — so moving to MariaDB neither weakens nor strengthens the `(merchantId, eventIdentity)` guarantee: rows with `eventIdentity = NULL` (money rows) do not participate on ANY candidate. The app's fail-closed guard (`EVENT_IDENTITY_REQUIRED` refuses any ATTRIBUTION without a 64-hex identity, `demand-credits.mjs` append()) remains load-bearing and remains sufficient; money rows are serialized by `(merchantId, seq)` where **both columns are NOT NULL, hence fully constraint-enforced** [FP: schema + code]. | PG 10 default is the same NULLS-DISTINCT behavior. (`NULLS NOT DISTINCT` arrived in PG 15 — unavailable in PG 10, and Prisma does not emit it anyway.) Equal. |
| **Concurrent writes (400+ simultaneous)** | Server process with MVCC + row-level locks; no single-writer file lock. The measured SQLite failure class (whole-DB lock contention → 10/10 500s) is architectural in SQLite and absent here. Residual InnoDB modes: deadlock 1213 / lock-wait-timeout 1205 under insert storms on the hot `(merchantId, seq)` neighborhood — the app's contention regex already matches `deadlock|write conflict|P2034` [FP: `handoff.mjs:149`], and `CHAIN_POSITION_CONTENDED` tells callers to retry. **Must be re-measured on MariaDB (Q15).** | Equally capable concurrency architecture. Equal on paper; unpatched in practice. |
| **Migration tooling** | `prisma migrate deploy` fully supported; Prisma Migrate serializes concurrent runs with a **MySQL `GET_LOCK` advisory lock, 10 s timeout**, plus the `_prisma_migrations` history table [VD: prisma.io docs "Development and production → Advisory locking"; prisma-engines PR #1479]. (Galera clusters can't GET_LOCK — N/A: cPanel shared MariaDB is a single server [VD: prisma#19350].) | Supported (`pg_advisory_lock`) — equal, moot. |
| **Connection limits** | Namecheap publishes **no fixed `max_user_connections`**; CloudLinux **MySQL Governor clamps an abusive account to `max_user_connections = 30`** when LVE CPU triggers [VD: support.cpanel.net "MySQL Governor… max_user_connections"; Namecheap KB resource-overusage]. Prisma's default pool is `num_cpus × 2 + 1` per process [VD: Prisma connection-pool docs] — must be pinned explicitly (Q5, Q13). | Same LVE regime; PG governor tooling on shared cPanel is weaker/undocumented [UA]. |
| **Pooling options** | Prisma's built-in pool with `?connection_limit=&pool_timeout=` URL params; no external pooler exists on shared cPanel (no ProxySQL/pgbouncer). Adequate for a single-account, few-process Passenger app. | No pgbouncer on shared cPanel; same built-in-pool-only story. |
| **TLS** | Connection is loopback (`localhost`) inside the same account — traffic never leaves the box; TLS not required for this topology. Prisma `mysql://` supports `sslaccept` etc. if Remote MySQL were ever enabled (then TLS mandatory) [VD: Prisma connection-URL docs]. Host's MariaDB TLS config: [UA]. | Same loopback story; host PG TLS config [UA]. |
| **cPanel application connectivity** | **First-class citizen**: cPanel "MySQL(R) Databases" UI creates DB/user/grants; `DATABASE_URL=mysql://user:pass@localhost:3306/db` in Setup Node.js App env panel (env vars persist across Passenger respawns — [FP: FEASIBILITY row 8]). | Second-class: cPanel's bundled PostgreSQL (9.2.24) was formally **deprecated in cPanel & WHM v102 and still listed deprecated in v118 release notes**; PG on cPanel depends on OS-repo builds [VD: docs.cpanel.net 102/118 release notes]. Weaker panel tooling, weaker future. |
| **Backup & PITR** | `mariadb-dump --single-transaction` gives a consistent InnoDB logical snapshot without blocking writers [VD: MariaDB docs]; schedulable by cron (host allows ≥5-min interval, ≤5 jobs [FP: FEASIBILITY row 7]); Namecheap AutoBackup included on Stellar Business [VD: Namecheap KB 9347]. **Point-in-time recovery is NOT available** — shared users have no binary-log or SUPER access; recovery granularity = last dump [VD-implied + UA on exact host config; treat as: plan for dump-granularity loss]. | Same shared-hosting ceiling: pg_dump yes, WAL archiving/PITR no. EOL additionally means restore targets stay unpatched. |
| **Restore procedure** | Create empty DB in cPanel → `mysql db_name < dump.sql` in Terminal (or cPanel Backup restore) → verify (Q8). | Analogous (`psql < dump`), moot. |
| **Operational support** | The **default database of the entire cPanel/WordPress shared-hosting world** — host staff tooling, Governor, docs, and Namecheap KBs all assume it. | Namecheap lists PG databases only on Plus/Business plan tables [VD: KB 10112]; provider operational attention is demonstrably thinner. |
| **Future scale** | Clear ladder: same schema moves to any managed MySQL/MariaDB (or the app re-targets `postgresql` provider on a SUPPORTED version later — Prisma schema is the portable source of truth). | Anything built against PG 10 must migrate twice (off the version, then off the host). |
| **Version support / upgrade path** | 11.4 is an **LTS maintained until 29 May 2029** [VD: mariadb.org/11-4-lts, release notes]; **11.4.9 released 2025-11-06** [VD: MariaDB 11.4.9 release notes] — the host tracks current LTS point releases. Server upgrades are the provider's job on shared. App side: **stay on Prisma 6.x; Prisma 7 upgrade is gated on prisma#29023 (open)**. | **EOL 2022-11-10; final release 10.23** [VD: postgresql.org/support/versioning + 10.23 announcement]. No upgrade path exists on this host — the host would have to install a new PG, which we cannot provision. Fails this axis outright. |
| **Deployment simplicity** | Minutes in cPanel UI; no daemon to run; artifact pipeline unchanged (Prisma query engine binary is the same `rhel-openssl-1.1.x/3.0.x` bundle already pinned for CageFS [FP: schema `binaryTargets`, `app.js`, `env.production.example`]). Bootstrap changes from "copy template .db" to `prisma migrate deploy` + existing idempotent init/seed scripts. | Similar simplicity, but on a deprecated panel component and dead upstream. |
| **Failure behaviour** | Fail-loud and diagnosable: too-many-connections (1040/1226 → Prisma P2037), deadlock 1213 (retryable; app already matches), lock-wait 1205, data-too-long 1406 under strict mode (refuses instead of truncating — [UA: strict mode on host, verify `sql_mode`]). InnoDB crash recovery via redo log. **Caveat vs PG:** MariaDB DDL is not transactional — a migration that dies mid-flight leaves partial DDL; `_prisma_migrations` marks it failed and `prisma migrate resolve` + restore path recovers (Q9). | PG has transactional DDL (genuine PG advantage, honestly noted) — but crash-recovery code that will never receive another fix is not a safety property. |
| **Data portability** | `mariadb-dump` SQL + Prisma-level export; the ledger's own `exportForMerchant()` emits DB-agnostic JSON [FP: demand-credits.mjs]. Initial SQLite→MariaDB data move should go **through Prisma clients (read old / write new), not SQL-dialect translation**. | pg_dump equally portable, moot. |
| **Rollback** | Release rollback never touches the DB ([FP: `deploy.sh`/`rollback.sh` — data lives in `~/orderweeddc-data`, releases swap around it]; same property preserved: DB lives in the MariaDB server, outside every release). Schema rollback = restore-from-dump or forward-fix (Q9). | Same mechanics, moot. |
| **Security maintenance** | Patched LTS stream to 2029; minor updates applied by host/CloudLinux. | **None since 2022-11-10. Disqualifying for a system whose core table is money-adjacent, multi-tenant, and internet-facing.** |

### Why not "neither"?
MariaDB 11.4.9 satisfies every application requirement without weakening one constraint, so the "name a deployable alternative off-host" clause is **not triggered**. For the record: if the host had offered only PG 10.23, the correct answer would have been an external managed database (or different host), never an EOL engine and never a diluted schema.

### Schema/port changes the migration lane must make (findings only — this lane edits nothing)
1. `datasource db` provider `"sqlite"` → `"mysql"` (same `env("DATABASE_URL")`).
2. Add `@db.Text` (or `@db.LongText` where >64 KB is plausible) to unbounded, **non-indexed** text columns, else Prisma's MySQL default `VARCHAR(191)` will refuse long writes [VD: Prisma MySQL type mapping]. Minimum set from schema read [FP]: `DemandCreditEntry.evidenceChain` (up to 64 links of JSON — the critical one), `AuditLog.details`, `Article.content`, `StagingABCARetailer.rawJson`, `SiteObservation.evidence/summary/uncertainty/preparedAction/title`, `Dispute.oldValue/newValue/reason`, `Product.description`, `Deal.description`, `Retailer.hours`(safe at default)/`address`, `Brand.description`, `LicenseEvidence.notes`, `ClaimRequest.requestedPasswordHash`(60 chars — fine at default). Rule: indexed/unique strings stay ≤191 chars (all hashes are 64-hex: `entryHash`, `eventIdentity`, `tokenHash`, digests — fine).
3. Adopt real migrations: repo currently has **no `prisma/migrations/`** and uses `prisma db push` [FP: `apps/web/package.json`, prisma dir listing]. Create a baseline `init` migration; production applies via `prisma migrate deploy`.
4. Port SQLite-specific utilities: `scripts/db-inspect.mjs` (queries `sqlite_master`) → `information_schema.tables`; `src/lib/db-config.mjs` PRAGMA courts are SQLite-only and must be provider-gated; `deploy/namecheap/bootstrap-production-db.sh` (copies a template `.db` file) must be replaced by a MariaDB bootstrap (`migrate deploy` + existing idempotent `init-production-db.mjs` + `seed-abca-retailers.mjs`, which are Prisma-level and portable) [FP: script reads].
5. `deploy/namecheap/env.production.example` needs a `mysql://` variant; `app.js`'s engine pinning and fail-loud `DATABASE_URL` check carry over unchanged [FP].

## THE FIFTEEN GATE QUESTIONS

**1. Which database and version?**
MariaDB **11.4.9** (host-provided, current LTS series; 11.4.9 released 2025-11-06 [VD]), Prisma provider `mysql`, Prisma pinned to the 6.x line (6.19.3 today). PostgreSQL 10.23 rejected (EOL 2022-11-10 [VD]). SQLite retained ONLY for local dev/test, per existing `LOCAL_TEST_DATABASE_ONLY` classification [FP].

**2. Why stronger for THIS application?**
(a) **Patching**: the ledger holds merchant money-equivalents and tenant boundaries; MariaDB 11.4 receives security fixes until 2029-05-29, PG 10 receives none [VD]. (b) **The load-bearing guarantee survives intact**: InnoDB enforces both composite uniques atomically under concurrency with the same NULLS-DISTINCT semantics the code was audited against — no behavioral drift, no schema dilution [VD+FP]. (c) **Concurrency architecture**: replaces the measured single-writer failure mode (10/10 500s) with row-level locking; the app's existing P2002/`CHAIN_POSITION_CONTENDED`/retry design maps 1:1 [FP]. (d) **Host fit**: cPanel's first-class DB with real panel tooling and provider operational muscle, vs a panel-deprecated PG lineage [VD]. (e) **Prisma maturity**: MariaDB 11.x explicitly listed; migrations serialized via GET_LOCK; the one known MariaDB-11 Prisma bug is v7-only [VD].

**3. Which app features depend on it?**
The Demand Credit ledger (issue/spend/refund/attribute + chain verification + merchant export, `demand-credits.mjs`); `/api/v1/attribution` idempotency under concurrent storms; the handoff route's graded evidence writes (`[domain]/retailer/[id]/handoff`); multi-tenant menu isolation via the `Brand → BrandMenu → MenuEntry → Retailer` join; sponsorship entitlement resolution (recomputes `entryHash`); public-write abuse reservations (`PublicSubmissionEvent`); sessions, loyalty, disputes, claims, audit logs; provenance/truth-status columns on every operational model [FP: schema + 16 referencing files].

**4. What constraints are database-enforced?**
`DemandCreditEntry`: PK `id`, `@@unique(merchantId, seq)` (gapless chain positions — both NOT NULL), `@@unique(merchantId, eventIdentity)` (attribution idempotency; NULLs exempt by design on all candidates), `entryHash @unique`. Plus: `Brand.domain`, `User.email`, `Session.tokenHash`, `Retailer.licenseNumber`, `Article.slug`, `StagingABCARetailer.licenseNumber` uniques; composites `MenuEntry(retailerId, productId)`, `BrandMenu(brandId, menuEntryId)`, `LoyaltyAccount(userId, brandId)`, `PublicSubmissionEvent(surface, subjectDigest)`, `SiteObservation(snapshotId, observationKey)`; FK integrity with `Cascade`/`SetNull` [FP: schema]. Not DB-enforced (app-enforced, unchanged): append-only-ness, balance ceilings, hash-chain continuity, ATTRIBUTION identity presence (fail-closed guard).

**5. Connection exhaustion behaviour?**
MariaDB refuses new connections with 1040/1226; Prisma surfaces pool/connect failures as P2037/P1001/P2024; in-flight committed work is unaffected — requests fail loudly, data stays consistent (contrast SQLite, where contention corrupted availability of the whole write path) [VD+FP]. CloudLinux MySQL Governor can clamp the account to `max_user_connections=30` under CPU abuse [VD: cPanel support doc]. Therefore: pin `connection_limit` explicitly (e.g. `?connection_limit=5&pool_timeout=15`) so even several Passenger processes stay far below 30; Prisma's default (`cpus×2+1` per process) must not be left implicit [VD].

**6. How are migrations serialised?**
`prisma migrate deploy`, run manually by the single operator in cPanel Terminal, records history in `_prisma_migrations` and takes a MySQL **GET_LOCK advisory lock (10 s timeout)** so two concurrent invocations cannot interleave [VD: Prisma docs "Advisory locking"]. `PRISMA_SCHEMA_DISABLE_ADVISORY_LOCK` must NOT be set. Precondition: create the baseline migration (repo currently uses `db push` with no migrations directory) [FP].

**7. How are backups created?**
Layered: (1) cron job (host allows ≥5-min intervals, ≤5 jobs [FP: FEASIBILITY]) running `mariadb-dump --single-transaction --routines <db> | gzip` to `~/backups/` with rotation + sha256; `--single-transaction` yields a consistent InnoDB snapshot without blocking writers [VD]; (2) Namecheap AutoBackup (included on Stellar Business [VD: KB 9347]); (3) pre-change manual dump before every `migrate deploy` (the bootstrap script's "backup before touching anything" discipline carries over [FP]). Off-box copies: operator downloads dumps periodically — a backup that lives only on the host is not a backup.

**8. How is a backup restored?**
(1) Put app in maintenance (stop accepting writes / restart with maintenance flag); (2) create a fresh empty DB in cPanel MySQL Databases (or drop/recreate tables); (3) `mysql <db> < dump.sql` in cPanel Terminal (or cPanel Backup restore UI); (4) verify: `prisma migrate status` clean; ported `db-inspect` shows expected tables + core inventory; run ledger `verifyChain` per merchant — the hash chain makes a truncated or tampered restore *detectable*, which is a property most apps don't get [FP: demand-credits.mjs]; (5) health-check `/api/health`, then re-open traffic. Accepted loss: everything after the dump (no PITR on shared hosting).

**9. How is rollback performed?**
Application: `sh ~/apps/orderweeddc/rollback.sh` swaps `current ← previous` and never touches the DB [FP: deploy.sh/rollback.sh; property preserved since data now lives in the MariaDB server, outside all release dirs]. Schema: Prisma has no automatic down-migrations; policy is (a) **expand-contract** — additive migrations only while old release must still run, destructive contraction in a later release, so app rollback needs no schema rollback; (b) if a migration must be reverted: restore pre-migration dump (Q8) or apply a forward migration generated with `prisma migrate diff` and reconcile history with `prisma migrate resolve`. Note honestly: MariaDB DDL is non-transactional — a mid-flight migration failure leaves partial DDL; the pre-migration dump (Q7 step 3) is the hard floor [VD+reasoned].

**10. How is staging isolated from production?**
Separate cPanel database + separate MySQL user (`cpuser_owdstage` / `cpuser_owdstage_u`) whose grants cover ONLY the staging DB; separate Node app root + subdomain + own env panel with its own `DATABASE_URL`; prod credentials never appear in the staging panel. Isolation is logical (same MariaDB server, same LVE budget — staging load can starve prod CPU/IO [FP: FEASIBILITY row 3]); heavy load tests belong off-host.

**11. How are secrets supplied?**
DB password is generated in cPanel's MySQL Databases UI (OWNER action) and entered ONLY into Setup Node.js App → Environment variables as part of `DATABASE_URL`; cPanel persists env vars across Passenger respawns [FP: FEASIBILITY row 8, env.production.example policy "NO SECRETS IN GIT"]. Unlike the SQLite file-path URL, `DATABASE_URL` now CONTAINS a secret — it must never be committed, logged, or echoed in receipts; `app.js` already fails loudly when it is missing [FP].

**12. How is the schema fingerprint verified?**
Three layers: (1) `_prisma_migrations` stores a checksum per applied migration; `prisma migrate status`/`migrate deploy` warn on modified history [VD]; (2) drift check: `prisma migrate diff --from-url "$DATABASE_URL" --to-schema-datamodel prisma/schema.prisma --exit-code` compares live DB to the schema at HEAD; (3) app layer: ported `db-inspect.mjs --assert-core` (via `information_schema`) plus `receipt.json` binding the artifact to its `gitSha` [FP], plus the ledger's own `verifyChain` replay for the money table's content integrity [FP].

**13. How does cPanel connect?**
`DATABASE_URL="mysql://<cpuser>_owd:<PASSWORD>@localhost:3306/<cpuser>_orderweeddc?connection_limit=5&pool_timeout=15"` — loopback TCP on the same box (a `socket=` variant also exists if the host's socket path is confirmed). Prisma's already-bundled `rhel-openssl-1.1.x`/`3.0.x` query engines and the `PRISMA_QUERY_ENGINE_LIBRARY` CageFS pinning are connector-independent and carry over unchanged [FP: schema binaryTargets, app.js, env example]. Remote MySQL (off-box) stays disabled unless a future need arises — then TLS becomes mandatory and unverified items in Q15 apply.

**14. What requires OWNER action?**
(1) Create the production database, DB user, and grants in cPanel; generate the password. (2) Enter `DATABASE_URL` (and confirm the other env vars) in Setup Node.js App. (3) Approve the code changes (provider swap, `@db.Text` annotations, baseline migration, ported scripts) — repo edits are outside this lane. (4) Run the first `prisma migrate deploy` + `init-production-db.mjs` + ABCA seed in cPanel Terminal. (5) Create the staging DB/user. (6) Confirm AutoBackup entitlement is active and set up the dump cron + off-box download habit. (7) Decide the fate of any existing `prod.db` data (import through Prisma, or start clean). (8) Confirm with Namecheap the account's database-size AUP ceiling (10 GB total for DBs+dumps is reported secondhand) and steady-state `max_user_connections`. (9) Verify PostgreSQL is simply left unused (no action needed to "turn it off" — do not create PG databases).

**15. What remains UNPROVEN?**
- **Concurrency on the real host**: the 400-simultaneous-write idempotency and handoff results were measured on SQLite post-repair [FP]; they MUST be re-run against MariaDB (locally in CI against MariaDB 11.4, then a bounded smoke on the host). Until then, "MariaDB fixes the concurrency classification" is an expectation, not a measurement.
- **InnoDB deadlock rate** on the hot `(merchantId, seq)` insert path under storms; the retry surface exists [FP: handoff.mjs regex] but its MariaDB behavior is unmeasured.
- **Host `sql_mode`** (strict vs permissive): strict is the modern default; if the host runs permissive mode, oversized writes could silently truncate instead of failing — must be probed (`SELECT @@sql_mode`) before first deploy.
- **Steady-state `max_user_connections` / `max_connections`** on the specific server (only the Governor clamp-to-30 behavior is documented [VD]).
- **Passenger process count** on Namecheap shared (pool-size multiplier) [FP notes maxEntryProc 40 but not app-process count].
- **Host MariaDB server variables** (`max_allowed_packet` — matters for 64-link evidence chains; buffer pool size) and TLS enablement.
- **AutoBackup actual schedule/restore granularity** ("ideally twice weekly, not guaranteed" per third-party reporting; entitlement wording from Namecheap KB) — verify by performing one real test restore.
- **The 10 GB database AUP ceiling** — reported secondhand from Namecheap's Disk Usage Provision; confirm current policy text.
- **PostgreSQL 10.23's exact behavior on-host** — untested and intentionally so; testing it would not change the EOL disqualification.
- Whether MariaDB minor updates (11.4.x → 11.4.y) are applied by the provider automatically and on what cadence.
